A warm-up with nothing to compile. The most common mistake in a dApp brought here from another chain is code that should not exist: waiting for confirmations, handling a reorganisation that cannot happen. This project asks for the explanation, because a builder who can explain why that code is missing will not add it back.

<StepCard n={3} title="Check the answer against this list">
<StepPart kind="gets">
The six things an indexer on this network does, and the four things it deletes.
</StepPart>
<StepPart kind="do">
1. **Treat the receipt as final.** Keep a pending state only for the seconds between send and receipt, and poll for the receipt; there is no block time to sleep for.
2. **Be idempotent against yourself.** With no reorganisations, the only way an event reaches your code twice is your own retry, a restarted worker or a duplicated webhook. Key every write on the transaction hash plus the log index.
3. **Never infer order inside a block.** A block is a super block combined from many governors' proposals. The 2021 paper documents an ordering rule for its own design, Redbelly has told me it changes in Q4 2026, and nothing you build should depend on it.
4. **Expect bursts and silence.** Blocks come when there is traffic: minutes of nothing, then several blocks seconds apart. Do not alert on "no new block for two minutes".
5. **Read events, not traces.** The RPC serves no `debug` or `trace` methods, so events and `eth_getLogs` are your only view, about 100 blocks a call. This is why the scaffold emits an event on every state change that matters.
6. **Record the genesis hash.** At start-up, compare it and refuse to continue on a mismatch. A testnet reset is not a reorganisation, and a reorg handler would not help you with one.

Delete from a ported indexer: the confirmation-depth setting, the canonical-chain table, the parent-hash walk that detects a reorganisation, and the unwind path. Keep the idempotency key.
</StepPart>
<StepPart kind="worked">
The answer in front of you has all six, in any words, and claims nothing beyond them.
</StepPart>
