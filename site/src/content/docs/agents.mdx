You use your own AI account and your own tool. This site hosts no model, proxies no prompts, and holds no API key and no deployer key. Everything here is a file, a package or a program that runs on your machine, and the two I consider most important are a text file and a rule.

This page is the home of the section for people who direct an agent and review what it produces. Everything about working with AI on this site lives here or is linked from here: the rules files and the local MCP server below, three short guides drawn from the runs on record ([Say what you want](/agents-guide/say-what-you-want/), [Read what comes back](/agents-guide/read-what-comes-back/) and [What never goes into an agent](/agents-guide/what-never-goes-in/)), and the agent track of every [project](/tutorials/), where each prompt sits beside the record of what happened when it was run. If you would rather write the contract yourself, the other section is [Writing Solidity](/solidity/). The two are not rivals: both end at the same tests, the same pre-flight and the same refusals, and a good reviewer of an agent's diff has usually read the Solidity path once.

## The rules file

One typed source in `packages/agent-rules/src/source.ts` renders to every format the common tools read. The five files share one body byte for byte; only the heading, one paragraph about the tool and Cursor's front matter differ. The package's own tests fail if a committed sample stops matching the renderer, and this site's build fails if a published copy stops matching the sample. Copy the one your tool reads, or run the CLI and get all of them.

```sh title="Every format, from npm (run 18 Sep 2026 against the public registry)"
cd /path/to/your/project
npx -y @gatedpath/agent-rules --out .
```

## MCP server

`@gatedpath/mcp` (`packages/mcp/`, bin `redbelly-mcp`) is a local stdio process on the official MCP SDK. It opens no port, has no hosted variant, sends no telemetry, makes no model call and holds no API key. There are fourteen tools. The read-only ones are `chain_info`, `is_verified` (`permission.isAllowed`), `gas_estimate_usd`, `preflight` (runs the CLI, returns its report), `five_state_tests` (every test contract that inherits `GatedTest`), `rules_files_check` (drift), `docs_lookup` (thirty topics to a URL on Vine or docs.redbelly.network plus one quoted consequence line, never fetched), the two from wave 7 below, and from wave 8 `doctor` and `gas_report`, with `ship_report` the one tool that writes a file. Signing through forge with a keystore name: `deploy_testnet`, which reads `eth_chainId` and refuses 151 outright, runs pre-flight and refuses on any fail, then broadcasts; and `verify_routescan`, a dry run by default. Every schema is strict, and before any handler runs the arguments are walked by pre-flight's secret scanner: anything key-shaped is refused by the name of the argument, never its value (a transaction hash, which has a key's shape, is allowed only in `explain_failure`'s `txHash`, and only ever read). There are thirty-three tests, including an end-to-end `deploy_testnet` on an anvil with chain ID 153 and a mined `NotEligible` revert explained from its hash.

### status and explain_failure

`status` takes the project path and answers `{ compiles, tests: { passed, failed, fiveState }, slither: { present, fresh }, rulesFiles, deployments: { local, 153, 151 }, next: { step, command, why } }`. It runs `forge build` and `forge test --json` locally, reads the Slither report and its sources hash, checks the five rules files against the render, reads `deployments/local.json` (what `npm run dev` writes), the `deployments/<chain>-<Name>.json` records and forge's `broadcast/` folders, and makes no network call unless you pass `rpc`, in which case pre-flight runs read-only against it and Routescan is asked whether a testnet deployment is verified. `next` is the first step not done in the fixed order compile, tests, five-state tests, Slither, rules files, pre-flight, testnet deploy, verify, ship report, with the exact command. Where the step signs, `why` says it needs a keystore of your own; the tool never invents a keystore name and never signs. An agent that calls it before each turn works from that answer rather than guessing the workflow. The recorded run on a fresh scaffold, step by step, is `packages/mcp/reports/wave-7-run-2026-09-14.md`.

`explain_failure` takes one of `revert` (hex data or the message a tool printed), `txHash` with `chain` (the receipt is read; a status-0 transaction is replayed with `eth_call` at its block to recover the revert data, and a `NotEligible` revert is followed by a read of the verifier's `eligibilityStatus`, which on a `ReceptorMock` names the credential state), or `stderr` (a pasted forge, cast, anvil, `npm run dev` or `redbelly-preflight` failure). It answers `{ kind, plainWords, cause, fix: { command?, link? } }` from the one table on the [errors page](/errors/). Unknown input answers `kind: "unknown"` with the raw text, never a guess. Read-only always; with `rpc`, an RBNT failure carries the current price through `gasCostUsd`. The same table ships in the frontend kit as `explainError(error)`, so the scaffold's web app shows the words instead of a hex revert.

### doctor, gas_report and ship_report

`doctor` is `redbelly-doctor` in-process: Node 22 or later; `forge`, `anvil` and `cast` on PATH, one version, and the real binaries rather than the `@foundry-rs` npm shim that exits 0 whatever the binary returned (the server probes with a flag no binary knows: the real ones exit 2, the shim 0, and the fix names the platform binary to link); `slither` and `aderyn` optional; git; no `.env` tracked; in a scaffold, `vendor/` against the version record the scaffolder writes. One entry per check with the fix from the same failure table, so a pasted doctor line and `explain_failure` agree. `gas_report` is `redbelly gas`: the project's `.gas-snapshot` or `forge test --gas-report --json`, every row priced at the chain's latest base fee and feed price in RBNT and US cents, with `diff` against a previous file. `ship_report` is `redbelly ship`: pre-flight with the keystore's address, the Slither sidecar, the tests and the five-state suites, the gas report, the deployer and admin readings, written to `deployments/ship-<chain>-<date>.md` only when every check passes; the deploy script refuses a broadcast on 151 without today's, and `status` reads the report's header for its last step. An agent's mainnet turn is `status`, then `ship_report`, then the `forge script` line `status` gives it, which signs with the keystore and never through this server.

It is on npm as `@gatedpath/mcp`, published on 18 September 2026, and `npx -y @gatedpath/mcp` starts it; I ran that against the public registry the same day and it answered with its fourteen tools. ## The key-handling rule

The MCP server, and every tool we add after it, never receives a private key. Tools that sign (deploy, verify, admin actions) take a Foundry keystore account name or a hardware wallet path and shell out to `forge` and `cast`, which sign locally. Faucet and eligibility-status tools take a public address and nothing else. A read-only step never escalates into one that signs. This is a hard rule, and it is in the rules file as well, so your agent holds it too.

A hosted chat-with-the-docs widget (`llms.txt` and your own agent cover it), a cloud deploy button, any flow that asks for an API key, any telemetry that leaves your machine without an explicit opt-in. Each would make this site a custodian of something, and I have designed it not to be one.
