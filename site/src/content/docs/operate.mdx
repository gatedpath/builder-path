Section 6 of the plan ends with "Operate": monitoring on the events the contract kit emits, an on-call contact, a published `security.txt`, a disclosure address and a rehearsed pause procedure. This page is the tooling for the first and last of those. The kit is `packages/ops-kit`. I ran everything on this page on 12 September 2026 against a local anvil or the public Routescan API; nothing has yet run against a contract of ours on either network, because none is deployed.

## The alert recipe

This is one script. It needs no service and no account with anyone. It polls `eth_blockNumber` every fifteen seconds, and when the head has moved it asks `eth_getLogs` for the contract's watched topics since the last block it saw, decodes each log and POSTs it as JSON to the webhook URL in the environment. The last block lives in a small state file, so a restart neither re-alerts nor misses anything; there are no reorgs on this network, so a block seen is final and the file only moves forward.

```sh
export ALERT_WEBHOOK_URL=https://hooks.example/…    # Slack, Discord, PagerDuty, or your own receiver
node packages/ops-kit/scripts/alert.mjs --contract 0xYourToken --network mainnet --state /var/lib/redbelly-alert/state.json
```

`--once` makes it a cron job; `--dry-run` prints instead of posting; `--min-severity info` includes skipped distributions; `--rpc` pins one URL (a private node, or the anvil the test uses). On mainnet the reads go through the fallback helper below. Blocks on Redbelly are produced on demand, so a quiet contract costs one small call per poll and nothing else.

<StatusPill variant="verified" label="Tested on anvil, 12 Sep 2026" /> The kit's `alert.test.mjs` deploys the real `GatedERC20` and a `ReceptorMock` on anvil, produces every watched event on-chain, and checks the poller decodes them in order with their arguments, filters by severity, posts to a local webhook with `--once`, keeps its place in the state file and refuses to run with no webhook and no `--dry-run`. <StatusPill variant="pending" label="No live contract yet" /> Nothing of ours is on 151 or 153, so no alert has fired for a real event.

## The network's own contracts

Your dApp depends on four contracts that are not yours. The permission contract decides whether your users can transact at all, the price feed and the gas fee contract set what they pay, and the bootstrap registry says where the other three are. I asked Redbelly on 12 September 2026 how changes to them are announced. The answer, on 17 September, was that the code becomes source-available between Q4 2026 and Q1 2027 and that builders monitor for themselves. So the kit now does that.

```sh
export ALERT_WEBHOOK_URL=https://hooks.example/…
node packages/ops-kit/scripts/system-watch.mjs --network mainnet --state /var/lib/redbelly-alert/system-mainnet.json
```

It looks in two ways, because neither is enough alone. On every pass it takes a snapshot: the address the registry answers for `permission`, `pricefeed` and `gasfees`, a fingerprint of the code at each, and for the permission contract, which is an upgradeable proxy on both networks, the implementation behind it, the proxy admin, and the admin's owner. Comparing two snapshots catches a change even when nothing was emitted. It also reads the logs of the permission proxy and its admin since the last block it saw, 100 blocks at a time because the governors RPC refuses wider requests, which catches what a snapshot cannot: a role granted or revoked, and the transaction an upgrade happened in.

The first run keeps a baseline and posts nothing. After that each change is posted once, in the same JSON shape as the alert recipe, so one webhook serves both. If the webhook refuses an alert, the state file stays where it was and the next pass tries again. The default interval is five minutes and a pass costs about a dozen calls. `--show` prints the current snapshot and touches nothing; `--once` and `--dry-run` work as they do above.

<StatusPill variant="verified" label="Run against both networks, 17 Sep 2026" /> Read-only, from my own machine: a baseline and then silence on 151 and on 153. I then replayed the log reader over the previous 6,000 mainnet blocks. It found three events that nobody announced: at 04:05:25 UTC on 14 September 2026 the permission contract's `DEFAULT_ADMIN_ROLE` was revoked from one address and granted to another, and at 04:30:35 UTC the ownership of its proxy admin moved to that same address. The record is `packages/ops-kit/reports/system-watch-2026-09-17.md`. Ten tests cover it against a scripted chain, with no network and no Foundry.

An alert from this watcher is not your incident to fix. It is a reason to re-run pre-flight and the five-state tests against a fork at the new block, to check that `isAllowed` still answers for a wallet you know, and to read Redbelly's channels. If a gated call now behaves differently, pause and tell your users why. Role names other than `DEFAULT_ADMIN_ROLE` show as their hash, because the contract's source is not published.

## Routescan for what happened

Routescan indexes both networks and its API answers keyless at two requests a second (measured on 15 September 2026; see SOURCES.md in the repository). Three scripts in the kit wrap the calls an operator makes most: the transfers of a token, its holders, and whether the source at an address is verified and is what you deployed.

```sh
node packages/ops-kit/scripts/routescan-transfers.mjs 0xToken --network mainnet --limit 50
node packages/ops-kit/scripts/routescan-holders.mjs   0xToken --network mainnet
node packages/ops-kit/scripts/routescan-verified.mjs  0xToken --network mainnet --expect-name GatedERC20 --expect-compiler 0.8.30
```

<StatusPill variant="verified" label="Run against mainnet, 12 Sep 2026" /> The recorded run in `packages/ops-kit/reports/` is against WRBNT, the busiest ERC-20 on 151 that day, because none of ours exists yet; the verified-source check on Multicall3 is in the same file. A holder list from an explorer is a snapshot of the `Transfer` events it indexed; for a gated token the on-chain truth is `balanceOf`, and eligibility is a separate read, `isEligible`.

## An RPC that fails over

Vine lists three public mainnet RPCs: the governors endpoint, Ankr, and Uniblock with a key on the `x-api-key` header. The kit's helper tries them in that order and moves on from a network error, an HTTP error, a timeout or a non-revert JSON-RPC error; a revert comes back from the first provider that answers, because every provider would say the same. Without a Uniblock key the provider is left out rather than tried, so nothing keyless ever goes to the keyed endpoint on your behalf.

## The runbook

`packages/ops-kit/runbook/INCIDENT-RUNBOOK.md` is written for the on-call person at three in the morning: what each alert means and whether it is an incident, five steps (confirm in ten minutes, pause, contain, tell people, recover and record), the `cast` and script commands they need, the quarterly drill, and a table to fill in once. It assumes the contract kit's Safe plus timelock layout, where pausing is one Safe transaction and unpausing waits out the timelock.

It ran on a local anvil, not on a network, and says so in its first paragraph.
