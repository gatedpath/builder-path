On most chains "who may call this" is an allow-list you keep. Here it is a question you ask: is this wallet eligible for this request id. The `Gated` base asks it for you. This tutorial reads the base, reads the smallest contract that uses it, and runs that contract's tests.

<ProjectSteps slug="solidity-gate-a-function" title="1. Gate a function" backHref="/solidity/" backLabel="Writing Solidity">

<StepCard n={1} title="Read the question your contract asks">
<StepPart kind="gets">
The whole interface between your contract and the identity system, which is smaller than you expect.
</StepPart>
<StepPart kind="do">
Your contract never sees a credential, a name or a date of birth. It holds a verifier's address and a request id, and asks the verifier one thing.

<Sample id="verifier-interface" />
</StepPart>
<StepPart kind="worked">
You can say what `isEligible(wallet, requestId)` returns and that nothing personal crosses the interface. The five states behind that answer are the subject of the next tutorial.
</StepPart>

<VineAside href="https://vine.redbelly.network/identity/eligibility/" label="Vine: eligibility">
What a credential is, who issues it and how a proof reaches a verifier is Redbelly's to explain. The consequence for your code is only this: the verifier is a dependency you did not write, so its address is state you must be able to change, and changing it is an admin act.
</VineAside>
</StepCard>

<StepCard n={2} title="Read the two modifiers">
<StepPart kind="gets">
The two words you will actually type.
</StepPart>
<StepPart kind="do">
<Sample id="gated-modifiers" />

`gated` checks the caller. `gatedFor(account)` checks someone else, and you need it more often than you think: a transfer has a recipient, a payout has a beneficiary, and an ineligible wallet must not end up holding something through a door you forgot.
</StepPart>
<StepPart kind="worked">
You can name, for a function of your own, every wallet that ends up with something when it runs. Each of those needs a gate.
</StepPart>
</StepCard>

<StepCard n={3} title="Read a whole gated contract">
<StepPart kind="gets">
A complete, small contract to copy the shape of.
</StepPart>
<StepPart kind="do">
<Sample id="gated-counter" />

Three things to notice. The constructor hands `Gated` a verifier and a request id, so which credential the gate asks for is decided at deploy time and not in the code. `_authorizeVerifierChange` is where you say who may repoint the gate; the base has no owner of its own, so if you leave it out the contract does not compile, which is better than an open door. And `tryIncrement` shows the other path: ask without reverting, record the denial, carry on.
</StepPart>
<StepPart kind="worked">
You can explain why `tryIncrement` exists. A reverted transaction keeps no events, and this network's RPC serves no trace methods, so a revert's reason cannot be read back from the chain afterwards. When a denial has to be on the record, it must not revert.
</StepPart>
</StepCard>

<StepCard n={4} title="Run it">
<StepPart kind="gets">
Proof on your own machine that the example does what it says.
</StepPart>
<StepPart kind="do">
From the repository's root:

```sh
cd packages/receptor-mock
npm run setup
forge test --match-contract GatedCounterTest
```
</StepPart>
<StepPart kind="worked">
`Suite result: ok. 9 passed; 0 failed`. One of the nine is `test_incrementAcrossAllFiveStates`, which the next tutorial takes apart. The whole package, `forge test` with no filter, is 34 passed and 1 skipped; the skipped one needs a live fork.
</StepPart>
<StepPart kind="ifnot">
`forge not found` means Foundry is missing, and a missing `lib/forge-std` means `npm run setup` has not run in this package. [When something fails](/errors/) has the rest.
</StepPart>
</StepCard>

<StepCard n={5} title="Write one of your own">
<StepPart kind="gets">
The habit, before the next tutorial teaches you to test it properly.
</StepPart>
<StepPart kind="do">
Copy `test/examples/GatedCounter.sol` beside itself under a new name and change what the gated function does: a guest book that stores one line per eligible wallet is enough. Keep the constructor, keep `_authorizeVerifierChange`, and put `gated` on the function that writes.
</StepPart>
<StepPart kind="worked">
`forge build` ends with `Compiler run successful!`; mine was twenty lines and compiled first time. You have not tested it yet, and an untested gate is not a gate; that is next.
</StepPart>
<StepPart kind="ifnot">
`Error (3656): Contract "GuestBook" should be marked as abstract`, pointing at `_authorizeVerifierChange() internal virtual;`, does not mean what it says. It means you have not written `_authorizeVerifierChange`, so you have not said who may move the gate. That is the base refusing to compile an open door.
</StepPart>
</StepCard>
