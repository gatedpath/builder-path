# When to use ERC-3643 instead

ERC-3643, the T-REX standard, is the permissioned-token standard most tokenisation platforms speak.
This kit is smaller on purpose. Here is where the line runs, and how Redbelly's credentials would
map onto ERC-3643's identity layer if you cross it.

## What ERC-3643 is

A suite of six contracts, not one: the token (ERC-20 compatible), an Identity Registry, its
Identity Registry Storage, a Trusted Issuers Registry, a Claim Topics Registry and a Compliance
contract. The token's transfer rule is that the sender has enough unfrozen balance, both parties
pass `isVerified()` on the Identity Registry (which means their ONCHAINID identity contract holds
valid claims on the required topics from trusted issuers), neither wallet is frozen, the token is
not paused, and the Compliance contract's `canTransfer()` says yes. It has `forcedTransfer()` (which
bypasses compliance but still needs a verified receiver), `recoveryAddress()` for a holder who lost
a key, `setAddressFrozen()`, `freezePartialTokens()` and `unfreezePartialTokens()`, `pause()` and
`unpause()`, and an agent role (`addAgent`, `removeAgent`, `isAgent`) for the operational functions.
Identity is ONCHAINID: per-holder ERC-734/735 contracts holding signed claims. The EIP reached Final
in July 2021. Source: eips.ethereum.org/EIPS/eip-3643, read 12 September 2026; the protocol's own
docs at docs.erc3643.org describe the same pieces.

## Prefer ERC-3643 when

- A transfer agent, custodian, exchange or tokenisation platform you must integrate with speaks it.
  Interoperability is the standard's strongest argument and it is decisive on its own.
- You need per-holder partial freezes, address freezes independent of credential status, or
  wallet recovery for a holder who lost a key. This kit has none of those; it has one lever
  (`forceTransfer`) and a policy that a lapsed credential freezes the whole balance.
- Your eligibility rules are many and change often: country limits, holder caps, lock-ups per
  tranche. ERC-3643's modular Compliance contract is built for that; this kit has one verifier and
  one request id, and changes go through a timelock.
- Your identity claims come from several issuers with different topics and you want that graph
  on-chain and inspectable.

## Prefer this kit when

- One credential decides eligibility and Redbelly's Receptor already answers it. The network has
  done the KYC; you need a boolean per wallet, not a claims graph.
- You want the smallest audited surface: 173 lines of source on OpenZeppelin, no proxies, no
  registry contracts of your own to run.
- You are on Redbelly specifically. Every holder here is already a verified wallet at the network
  level (`permission.isAllowed`), so ERC-3643's "is this wallet a known investor" layer is partly
  answered before your contract runs. What is left is the per-asset rule, which is what `Gated`
  binds to.

## Mapping Receptor onto ERC-3643, if you go that way

ERC-3643's Identity Registry answers `isVerified(address)` by looking up the wallet's ONCHAINID and
checking that it holds claims on every required topic from an issuer in the Trusted Issuers
Registry. Receptor's world has the same three nouns with different shapes:

| ERC-3643 | Receptor on Redbelly | Fit |
|---|---|---|
| Trusted Issuers Registry: issuer addresses allowed per claim topic | Accredited issuer registry on-chain (mainnet 0x2d68…4ac5, testnet 0x6aEe…A057, RESEARCH.md question 8) plus `allowedIssuers` DIDs in an Iden3 query | An adapter could populate the Trusted Issuers Registry from the accredited issuers; the DID to key mapping is not public today (question 15) |
| Claim Topics Registry: which topics a holder needs | The Iden3 query itself (schema, type, operator, value), for example `country $eq "AUS"` on a ProofOfAddress credential | One topic per request id; the query is the topic definition |
| ONCHAINID per holder with signed claims | No per-holder identity contract; the proof lands on the dApp's verifier as a record for `(wallet, requestId)` | The gap. An ERC-3643 Identity Registry would need a custom implementation whose `isVerified` reads the verifier (`Iden3VerifierAdapter.isEligible`) rather than an ONCHAINID, which is what this kit's `Gated` already does |
| `isVerified(address)` | `IRedbellyVerifier.isEligible(wallet, requestId)` | Direct |
| Compliance `canTransfer()` | Nothing network-level; your own rule | Write the module |
| Agent role | `COMPLIANCE_ROLE`, `PAUSER_ROLE`, `ISSUER_ADMIN_ROLE` split across Safes | ERC-3643 has one agent role; this kit has three |

So the practical route is an ERC-3643 token whose Identity Registry is a thin contract implementing
`isVerified` over the same `IRedbellyVerifier` this kit uses, with the Trusted Issuers and Claim
Topics registries kept for interoperability but populated to mirror the Iden3 query. That gives
the standard's interface to integrators without inventing an ONCHAINID per Redbelly holder. Nobody
has built it yet as far as the sources read on 12 September 2026 show; if you do, the five-state
test base in `receptor-mock` applies unchanged, because `isVerified` is just another gate.

## Two cautions

The T-REX reference implementation pins its own compiler and uses upgradeable proxies throughout;
check the solc version against Redbelly's 0.8.30 Prague target before assuming it deploys, and
budget the audit accordingly. And a private-credential design point: ERC-3643 puts claims on-chain
in the holder's identity contract, while Receptor's Proof by Query proves a predicate in zero
knowledge and leaves the credential with the holder. Mirroring claims into ONCHAINID would give up
that property; the adapter route above keeps it.
